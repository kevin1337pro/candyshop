# Update auf Candy Corner 2.3 — 25.09.2026

Für die bereits laufende Installation auf **https://vape.miami-enterprise.com**. Dieses Git-Update allein ändert den Server nicht. Im vorhandenen Repository-Verzeichnis arbeiten und dieselbe `.env`, denselben Compose-Projektnamen und dieselben Datenvolumes behalten.

## 1. Code und öffentliche Adresse

```sh
git pull --ff-only
nano .env
```

Bei einem bereits vorhandenen Reverse-Proxy auf dem Host:

```dotenv
COMPOSE_FILE=docker-compose.yml
SITE_URL=https://vape.miami-enterprise.com
SHOP_DOMAIN=vape.miami-enterprise.com
HTTP_BIND=127.0.0.1
HTTP_PORT=8080
```

**8080 bleibt ausschließlich der lokale Upstream-Port.** Browser, WordPress-Links, PayPal-Rücksprünge und Webhooks verwenden die öffentliche HTTPS-URL ohne Port. Kein `http://…:8080` in `SITE_URL` eintragen. Die Vorlage `.env.example` ersetzt keine bestehende `.env`; dort die Werte ausdrücklich ändern.

Der vorhandene Caddy auf dem Host kann so weiterleiten:

```caddyfile
vape.miami-enterprise.com {
    encode zstd gzip
    redir /wp-admin /wp-admin/ 308
    reverse_proxy 127.0.0.1:8080
}
```

Caddy setzt `X-Forwarded-Proto` und erhält den ursprünglichen Host. Die explizite Admin-Weiterleitung verhindert, dass Apache vor WordPress einen Redirect mit seinem internen HTTP-Schema erzeugt. Beim Abruf am 25.09.2026 war auf der Startseite kein `:8080` nachweisbar, aber `/wp-admin` leitete zunächst auf HTTP um. Die Prüfung nach dem Update umfasst beides.

Für einen Proxy in einem anderen Container ein gemeinsames Docker-Netzwerk und `wordpress:80` verwenden; `127.0.0.1` wäre dort der Proxy selbst. Nicht zusätzlich den mitgelieferten Caddy starten, wenn Ports 80/443 bereits durch euren Proxy belegt sind. Bei Verwendung unseres HTTPS-Overrides bleibt `COMPOSE_FILE=docker-compose.yml:docker-compose.https.yml`; beide Varianten nicht mischen.

## 2. Sicherung und Update

```sh
sh docker/update-shop.sh
docker compose logs --tail=80 setup
docker compose run --rm wpcli plugin list
docker compose run --rm wpcli option get home
docker compose run --rm wpcli option get siteurl
```

Das Skript erstellt zuerst mit `backup.sh` eine Sicherung (WordPress wird kurz angehalten), baut das Image, startet WordPress neu und führt die Einrichtung erneut aus. Dabei wird das offizielle PayPal-Plugin ergänzt, falls es im bestehenden Datenvolume noch fehlt, und aktiviert. Vorhandene Pluginversionen, Kontoverbindungen, Produkte, Bestellungen, Adminpasswörter und Lieferdaten werden nicht überschrieben. Bereits vorhandene PayPal-Versionen gezielt prüfen/aktualisieren; getestet wurde 4.1.3.

Die öffentliche URL wird bei Einzelinstallationen zusätzlich in den Datenbankoptionen `home` und `siteurl` synchronisiert; Laufzeitkonstanten allein können alte Werte verdecken. Bei Multisite werden die Domain-Zuordnungen bewusst nicht verändert: siehe `MULTISITE.md`. Der bestehende technische Theme-Ordner `forme` bleibt erhalten. **Kein `down -v`, keine neuen Datenvolumes und keine neu erzeugten Datenbankpasswörter für das Update.**

Alte, fest im Inhalt gespeicherte URLs sind gesondert zu prüfen. Nach dem Backup zunächst nur ein Probelauf mit der tatsächlich alten URL:

```sh
# Beispiel: nur ausführen, wenn dies wirklich die alte gespeicherte Adresse ist.
docker compose run --rm wpcli search-replace 'http://localhost:8080' 'https://vape.miami-enterprise.com' --all-tables-with-prefix --skip-columns=guid --dry-run
```

Die Ausgabe prüfen, erst danach bewusst ohne `--dry-run` ausführen. Keine pauschale Datenbank-Ersetzung auf einem Multisite-Netzwerk. Bei abweichendem Reverse-Proxy `Host` und `X-Forwarded-Proto` korrekt weitergeben. Die WordPress-Installation darf intern nicht direkt öffentlich erreichbar sein.

- WordPress: **Design → Rechtstexte & PayPal**. Die fünf Seiten werden als Entwürfe angelegt. `[[PLATZHALTER]]` und Bearbeitungshinweise ausfüllen/entfernen. Vorhandene Betreiberseiten werden nicht überschrieben. Beim ersten Setup oder Upgrade des aktiven Candy-Themes erfolgt der Entwurfimport automatisch; ansonsten dort den Importbutton verwenden.
- **WooCommerce → Einstellungen → Zahlungen → PayPal:** Geschäftskonto nach Erstellung verbinden. Keine Zugangsdaten in Git oder Chat eintragen. Zunächst Sandbox testen. Anleitung und Gebühren: `docs/PAYPAL.md`.
- SMTP-Anbieter einrichten. Empfänger für neue Bestellungen in WooCommerce und die WordPress-Admin-E-Mail für Widerrufe prüfen. Ohne funktionierenden Mailversand ist die vorgeschriebene unverzügliche Widerrufsbestätigung nicht sichergestellt.
- `vertrag-widerrufen` veröffentlichen und vom Footer aus ohne Anmeldung testen. Erklärung landet unter **WooCommerce → Widerrufe**; fehlgeschlagener Versand wird angezeigt und per WP-Cron wiederholt. Für zuverlässige Wiederholung einen echten Server-Cron für `wp cron event run --due-now` einrichten und Fehlversand überwachen. Der Cron ersetzt keine sofort funktionierende Mailzustellung.

## 4. Abnahme auf dem Zielserver

```sh
curl -I https://vape.miami-enterprise.com/wp-admin
curl -I https://vape.miami-enterprise.com/wp-admin/
curl -I https://vape.miami-enterprise.com/warenkorb/
```

Keine `Location` mit `:8080` oder Downgrade auf HTTP. Browser-/Proxy-Cache leeren; CSS-Version ist jetzt 2.3.0. Mobil das Bannerlogo und den Warenkorb prüfen. Checkout/Warenkorb/Widerrufsformular/`wc-ajax`/Woo-REST-Endpunkte und personalisierte Sessions nicht cachen.

Auf der bestehenden Domain wurden `Cross-Origin-Embedder-Policy: require-corp` und `Cross-Origin-Resource-Policy: same-origin` beobachtet. Solche pauschalen Isolations-Header können externe Zahlungs-Skripte/Frames verhindern. Für die PayPal-Kasse die tatsächlichen Browserfehler prüfen und insbesondere pauschales COEP entfernen, wenn es die Einbettung blockiert. Bei eigener CSP die von PayPal offiziell benötigten Quellen gezielt erlauben; keine pauschalen Wildcards setzen.

Testfälle: Lieferung 45127, Ablehnung 10115 und fremdes Land, Abholung, Warenwert unter/über 20 €, 5 € Lieferkosten, Barbestellung, PayPal-Erfolg/Abbruch/Erstattung, Webhook, Handy-/iPad-Mitteilung und zweistufiger Widerruf mit zugestellter E-Mail. Zahlungsstatus nur aus der bestätigten Plugin-Verarbeitung übernehmen. Hier wurden weder echte Zahlungen noch Änderungen an eurem produktiven Server durchgeführt.
